# GPU access for WASI containers: design

Status: **design, phase 1** (bibliography and decisions). Nothing here is
implemented yet. Every reference in the last section was opened while writing
this page; nothing is cited from memory.

The goal: a go-wasmcontainers container (a `wasip1` core module: Go
`GOOS=wasip1`, or C through wasi-libc) can use the local GPU for

1. **ML inference**,
2. **general GPU compute**,
3. **graphics rendering**, shown in a dashboard pane.

The playground (browser) is the primary target; the native engine (wazero,
`CGO_ENABLED=0`) is the second.

## Decisions

| Question | Decision | Why (reference) |
|---|---|---|
| ABI for inference | **wasi-nn witx**, module `wasi_ephemeral_nn`: `load`, `load_by_name`, `init_execution_context`, `set_input`, `get_output`, `compute` | It is a preview-1 (witx) interface, the shape of our guests [nn-witx]. Wasmtime still serves it to core modules, from the same file, through `wiggle` [wt-witx]. `get_output` writes into a guest-provided buffer, so the host never allocates in the guest. The WIT version (`wasi:nn@0.2.0-rc-2024-10-28`) uses resources and `list` results that need `cabi_realloc` [nn-wit]. |
| Encodings and targets | `onnx` first; `execution_target` `cpu` and `gpu` (witx enums: openvino, onnx, tensorflow, pytorch, tensorflowlite, autodetect / cpu, gpu, tpu) | The proposal places no requirement on hosts to support specific backends. Wasmtime picks a backend **by encoding** and passes the target through unchecked [wt-witx][wt-backend]. We do not pass it through unchecked: `gpu` with no GPU fails with `unsupported_operation`, and is never quietly run on the CPU. |
| ABI for compute and rendering | **`wasi:webgpu@0.3.0-rc.2`, lowered by hand to a core module** (the "core module + canonical-ABI host" path). Import module `wasi:webgpu/webgpu@0.3.0-rc.2`, names such as `[method]gpu-device.create-buffer`, `[resource-drop]gpu-buffer`, `get-gpu` | The WIT is the standard (Phase 2, WebGPU-shaped) [gfx-readme][gfx-wit]. A core module may import those names; the host implements the canonical ABI for them (16 flat params, 1 flat result, otherwise a pointer) [cabi]. Naming per [cm-names] and wit-bindgen-go's design notes [gm-design]. |
| Async functions in that WIT | **Sync lowering**: the guest calls `request-adapter`, `request-device`, `map-async`, `on-submitted-work-done`, `create-*-pipeline-async`, `pop-error-scope` synchronously and blocks | `wasi:webgpu` 0.3 marks them `async func` [gfx-wit]. The component model allows "synchronously calling an `async` function" (the caller blocks) [cm-async]. Async lowering (4 flat params, status code, waitable sets) is not needed. |
| Component-model runtime in the engine? | **No.** The engine stays a core-module host | wazero has no component model; mainline Go emits core `wasip1` modules. A component loader and linker is a project of its own. Honest limit: our guest is a core module importing WIT-named functions, not a component. Source compatibility holds; binary portability to a component runtime would need componentisation. |
| Guest bindings (Go) | **Our own**, `//go:wasmimport` over the canonical ABI, generated by a Go program from the WIT, for the subset we serve | wit-bindgen-go targets `GOOS=wasip1` [gm-changelog] but its last release is v0.7.0 (2025-05-25) and its function model has no `async` functions [gm-function], which `wasi:webgpu` 0.3 uses throughout. `go:wasmimport` accepts `float32`/`float64` and `structs.HostLayout` pointers [go-compile]. |
| Guest bindings (C) | Later; candidate `wasi-gfx/wasi-webgpu-headers` (a `webgpu.h` over `wasi:webgpu`) | Listed by the wasi-gfx project [gfx-org]; not evaluated yet. |
| Rendering ABI | `wasi-gfx:surface@0.2.0` + `surface-webgpu` (`context`: `configure`, `get-current-texture`, `present`), pinned to `wasi:webgpu@0.3.0-rc.2` | `surface` and `frame-buffer` left WASI for the `wasi-gfx:` namespace ("versioned like a library") [gfx-org]. There is no `wasi:graphics-context` any more: the WebGPU context is `surface-webgpu.context` [gfx-surface-webgpu]. `frame-buffer@0.2.0` (copy in/out) is the no-GPU fallback [gfx-fb]. Surface events are `stream<…>` [gfx-surface]; phase 2(c) starts with `present` paced by the host and no event streams. |
| Where WebGPU lives (browser) | **In the engine worker**, which already serves every WASI call. One `GPUAdapter` **and one `GPUDevice` per container** | The guest worker is blocked in `Atomics.wait` during a call (engine `runtime/browser/worker.js`), so it cannot await a promise; the engine worker can. `WorkerNavigator.gpu` exists in Chrome 144+ (113+ partial), Firefox 141+ (partial: Windows, Apple-silicon macOS; no Linux), Safari 26 [bcd-wn]. An adapter is "consumed" by `requestDevice`, so one per device [webgpu-spec]. A device per container isolates objects and `device.destroy()` frees everything at exit. |
| Sync guest vs async WebGPU | The existing **`wasi.Result.Wait` / `Resume`** mechanism: a WebGPU promise resolves → a channel closes → `Resume` writes the result and the guest is woken | This is how the engine serves WasmEdge sockets today (`wasi/wasi.go` `Result`, `runtime/browser/executor_js.go` "A socket wait"). JSPI is not needed (the guest's stack never has to suspend: its worker already blocks). One call costs one SAB round trip (playground README: 38 µs measured); to be measured per frame. |
| Data path | Guest memory is a shared `WebAssembly.Memory`; `queue.writeBuffer` takes an `AllowSharedBufferSource` [webgpu-spec], so uploads go from guest memory with no extra copy | |
| `cabi_realloc` | Needed for `list`/`string` results (e.g. `get-mapped-range-get-with-copy`, adapter info strings). Natively: the host calls the guest's export. Browser: the guest worker calls it on the host's request (a new reply flag), then the host resumes | Open risk R1 below. |
| Frames to the dashboard | Engine worker renders to its own `OffscreenCanvas` (`getContext("webgpu")`), `transferToImageBitmap()` on `present`, posts the `ImageBitmap` (transferable) to the page; the dashboard draws it in a surface pane | `OffscreenCanvas` webgpu context: Chrome 144, Firefox 141 (partial, Windows), Safari 26; `transferToImageBitmap`: Chrome 69, Firefox 105, Safari 16.4 [bcd-oc]. Avoids a GPU→CPU readback. `transferControlToOffscreen` of a DOM canvas was rejected: the dashboard is one go-widgets canvas. |
| Browser inference backend | **Ours**: the wasi-nn host runs ONNX graphs with its own operators, as WGSL compute kernels on the container's WebGPU device; the same operators in Go for the CPU | One codebase for both executors (the browser engine worker is Go too). Alternative kept: vendoring onnxruntime-web (MIT; no CDN needed, `env.wasm.wasmPaths` [ort-env]) — but its WebGPU build's wasm is 23.7 MB [ort-files] and it allocates on its own device, outside our quotas. WebNN is behind a flag in Chrome only, absent in Firefox and Safari [bcd-ml]: optional later. |
| Native, `CGO_ENABLED=0` | **wasi-nn: pure-Go CPU backend** (our ONNX subset; kernels from go-simd where they exist). **wasi:webgpu: no adapter** (`request-adapter` returns `none`) at first | gonnx: opset 13 only, MPL-2.0, Gorgonia tensors in its API [gonnx]; onnx-go last pushed 2024-09. A pure-Go WebGPU exists: gogpu/wgpu, "Zero CGO", Metal/Vulkan/DX12/GLES through its own FFI, MIT, no stable release stated [gogpu]. Evaluated after (b); until then native says "no adapter", never a CPU result labelled GPU. |
| Access control | **No GPU unless `wctr run --gpu`** (API: a field on the create request, to be named with the engine owner). Without it, `get-gpu` works but `request-adapter` returns `none`, and wasi-nn `load(target=gpu)` fails | Least privilege; a guest can test for the GPU portably. wasi-nn on CPU stays available, its memory counted against the container's limit. |

## Quotas and security

The browser already gives us, per the WebGPU spec [webgpu-sec]: zero-initialised
resources (no leftover data), bounds-checked shader access ("robust buffer
access" or inserted checks), validation of every call, a GPU watchdog that may
lose the device after "a few seconds", and quantised `timestamp-query`. It does
**not** give per-container limits: all containers share the page's GPU
process, and memory probing and workload identification are explicitly
unmitigated [webgpu-sec].

So the host mediates every call (no object reaches a guest except as a handle
in a per-process table, like file descriptors) and enforces:

| Quota (default, per container) | Enforced where |
|---|---|
| Handles: 4096 live objects | handle table |
| GPU memory: 256 MiB summed over buffers and textures (host-computed sizes) | `create-buffer`, `create-texture` |
| Limits: `requiredLimits` clamped to the quota (spec defaults: `maxBufferSize` 256 MiB, `maxStorageBufferBindingSize` 128 MiB [webgpu-spec]) | `request-device` |
| Features: none optional unless allowed; **`timestamp-query` refused** by default | `request-device` |
| WGSL source: 1 MiB per module; pipelines: 256 | `create-shader-module`, `create-*-pipeline` |
| GPU time: a submit not done within 2 s → the container is stopped and its device destroyed | `on-submitted-work-done` timer |
| Frames: `present` paced to ≤ 60 per second; surface ≤ 1920×1080 | `surface-webgpu.context` |
| wasi-nn: model ≤ 64 MiB, tensors ≤ 64 MiB, ONNX parser fuzzed | `load`, `set_input` |

Device loss (watchdog, driver reset, `destroy`) makes every later call fail
with the WIT's error results; the container is told, not hung. Timing: the GPU
queue can build high-precision timers from storage buffers whatever we do
[webgpu-sec]; we refuse `timestamp-query` and say so in the docs. Every
host-side decoder (canonical-ABI records, ONNX protobuf, WGSL size checks) gets
a fuzz target.

## Integration needs (owned by other repositories)

**engine, package `wasi` and executors** — a seam to register host modules
beside `wasi_snapshot_preview1`:

- a host module = an import module name + functions with **typed signatures**:
  params `i32`/`i64`/`f32`/`f64` (today only `i32`/`i64`), and **zero or one
  result of any of those four** (today always an `i32` errno);
- per-process state created with the `Proc` and closed at exit or kill
  (to destroy the GPU device);
- `Result` gains a return value and a **`Realloc` request** (size, align):
  natively the wazero executor calls the guest's `cabi_realloc` export; in the
  browser, `worker.js` calls it and posts the pointer back, then the host
  resumes;
- `worker.js` builds its import object per module (not only
  `wasi_snapshot_preview1`) and passes `f32`/`f64` through the control block;
- a container option (`--gpu`, API field) reaching `Config`.

**playground** — the engine worker registers this repository's browser host
(`GOOS=js`, `syscall/js` on `navigator.gpu`); posts each container's
`ImageBitmap` frames to the page; CSP unchanged (no network fetch for models:
they come from the image's filesystem).

**dashboard** — a **surface pane** per container surface: draws the latest
`ImageBitmap` scaled into the pane (go-widgets webcanvas needs an image-from-
bitmap primitive), shows "no GPU" / "device lost", and later forwards pointer
and key events.

## Open risks

- **R1 — `cabi_realloc` re-entry in Go guests.** A host calling a Go
  `//go:wasmexport` function while that guest is inside a `//go:wasmimport`
  call has not been verified; the Go runtime sources read so far do not settle
  it. First measurement of phase 2(b). Fallback: our bindings pass a
  guest-owned scratch buffer and avoid host-allocated results.
- **R2 — CI cannot prove a GPU path.** Linux has no Firefox WebGPU [bcd-wn];
  what headless Chromium exposes on a GPU-less runner (likely a fallback
  adapter, `isFallbackAdapter` [webgpu-spec]) is to be measured. Tests will
  record the adapter info and never call a fallback adapter "GPU".
- **R3 — call overhead.** One SAB round trip per WebGPU call; a render loop
  of ~20 calls is ~0.8 ms per frame at 38 µs. To be measured; batching would
  depart from the WIT.
- **R4 — moving target.** `wasi:webgpu` is `0.3.0-rc.2`; the version is
  pinned in the import module name, so a guest built for it keeps working
  until we drop that version.

## Plan

(a) wasi-nn: guest Go bindings, native CPU backend, browser backend (CPU
first, then WGSL kernels), example image classifying an embedded picture with
a tiny ONNX model, run in the playground. (b) `wasi:webgpu` compute: bindings
generator, browser host, vector add and matrix multiply checked against a CPU
result, throughput against a CPU baseline. (c) rendering: `surface-webgpu`,
dashboard pane, spinning triangle, paced frames. Each step: tests natively,
Playwright Chromium and Firefox in the browser, a release, README and docs.
